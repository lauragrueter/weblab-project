[[section-design-decisions]]
== Architekturentscheidungen
Im folgenden Kapitel werden die Architekturentscheidungen begründet. Diese sind in chronologischer Reihenfolge aufgelistet. Einige Entscheidungen wurden erst im Verlauf des Projektes getroffen, was ein Refactoring bestehender Codeabschnitte zur Folge hatte.

=== Angular als Frontend-Framework
**Entscheid**: Angular als Frontend-Framework

**Begründung**: 

- Neues Wissen aufbauen
- In der Blockwoche Gelerntes gleich umsetzen

**Konsequenz**:

- Höhere Lernkurve

=== NestJS als Backend-Framework
**Entscheid**: NestJS als Node.js-Backend-Framework

**Begründung**: 

- Architekturähnlichkeit zu Angular: Wechsel zwischen Frontend und Backend wird vereinfacht
- Vorgegebene Projektstruktur: Codestrukturentscheidungen werden vereinfacht
- TypeScript Unterstützung: Typisierung in frontend und backend (Fehlervermeidung)

**Konsequenz**:

- Höhere Lernkurve
- Erhöhte Durchgängigkeit im Projekt

=== PostgreSQL
**Entscheid**: PostgreSQL als relationales Datenbankmanagementsystem

**Begründung**: 

- Verbreitung: grosse Community und somit viele Informationen frei zugänglich
- Relationales Datenmodell: fitlog Daten sind strukturiert und gut geeignet für ein relationales Modell

**Konsequenz**:

- Schema muss definiert werden
- Installation etwas komplexer als z. B. bei MongoDB

=== TypeORM
**Entscheid**: TypeORM zur Datenbankabstraktion und Persistenz

**Begründung**: 

- NestJS Integration
- TypScript Integration

**Konsequenz**:
- TypeORM muss installiert werden

=== Docker Compose
**Entscheid**: Docker Compose zur Orchestrierung der Container für Datenbank, Backend und Frontend

**Begründung**: 

- Dev- und Bewertungsumgebung laufen in identischen isolierten Containern
- Datenbank bleibt isoliert und befindet sich nicht lokal

**Konsequenz**:

- Docker-Laufzeitumgebung wird auf den Zielsystemen vorausgesetzt
- Erstellung von `docker-compose.yml`- und `Dockerfile`-Konfigurationen

=== Angular Material
**Entscheid**: Angular Material als UI-Komponentenbibliothek

**Begründung**: 

- Fertige Komponenten können verwendet werden
- Integrierte Accessibility
- Einfaches Design

**Konsequenz**:

- Angular Material muss installiert werden
- Design sieht nach Angular Material aus

=== Testframeworks für Backend und Frontend
**Entscheid**: Vitest als Test-Runner für Frontend- und Backend-Unit-Tests

**Begründung**:

- Einheitliche Testwerkzeuge
- einfache Handhabung

**Konsequenz**:

- Konfigurationsaufwand für die Anbindung an Angular und NestJS

=== End-to-End-Testframework
**Entscheid**: Cypress für E2E-Tests

**Begründung**:

- Bereits aus dem Unterricht bekannt
- Gute Entwicklererfahrung und intuitive Handhabung bei der Testerstellung

**Konsequenz**:

- Einrichten und Pflegen der E2E-Testumgebung sowie der Testdaten

=== Strukturierung des Frontends
**Entscheid**: Gliederung des Frontends in die Ordnerbereiche `core`, `features` und `shared`

**Begründung**: 

- Klare Trennung von Zuständigkeiten (Separation of Concerns)
- Erhöhte Wartbarkeit und Übersichtlichkeit bei wachsendem Funktionsumfang
- Gezielte Wiederverwendbarkeit von Modulen

**Konsequenz**: 

- Wiederverwendbare UI-Elemente werden in `shared` ausgelagert
- App-weite Singletons, Services und Konfigurationen liegen in `core`
- Fachliche Domänen und Ansichten werden isoliert in `features` aufgebaut

=== Komponentenstruktur im Frontend (Inline-Templates)
**Entscheid**: Nutzung von Inline-Templates bei kleineren Komponenten

**Begründung**: 

- Höhere Übersichtlichkeit bei sehr kompakten Komponenten durch Bündelung in einer Datei
- Ausprobieren neuer Framework-Strukturen, um Erfahrungen zu sammeln

**Konsequenz**: 

- Uneinheitliche Dateienstruktur (einige Komponenten mit separaten HTML-Dateien, andere inline)
- Für Lehr- und Lernzwecke akzeptabel, bei komplexeren Komponenten wird jedoch weiterhin auf eine Dateitrennung gesetzt

=== Strukturierung des Backends
**Entscheid**: Verwendung einer Modularchitektur

**Begründung**: 

- Entspricht den gängigen Best Practices von NestJS
- Kapselung von fachlichen Domänen in eigenständige Module

**Konsequenz**: 

- Vorgegebene, aber saubere und erweiterbare Ordner- und Dateistruktur

=== Datumsverarbeitung (Workout)
**Entscheid**: Bereitstellung von zentralen Hilfsfunktionen für die Datumsformatierung

**Begründung**: 

- Direkte String-Umwandlungen mittels `new Date()` führten zu fehlerhaften Zeitzonen-Umrechnungen
- Zentrale Hilfsfunktionen können in allen Komponenten wiederverwendet werden

**Konsequenz**:

- Refactoring von bestehendem Code
- Vermeidung von redundantem Code und Zeitzonenfehlern

=== Shared Component: Create-Button
**Entscheid**: Bereitstellung des Create-Buttons als wiederverwendbare Shared Component

**Begründung**: 

- Der Button wird an mehreren Stellen in der Anwendung benötigt
- Verbesserung der Wartbarkeit und Erweiterbarkeit
- Gewährleistung eines einheitlichen Layouts
- Anpassung an einem Ort, falls nicht mehr Angular Material verwendet wird

**Konsequenz**:

- Refactoring des alten Codes
- Button kann wiederverwendet werden

=== Shared Component: Page Header
**Entscheid**: Bereitstellung des Page Headers als wiederverwendbare Shared Component

**Begründung**: 

- Der Header wird auf mehreren Seiten wiederverwendet
- Erhöhung der Wartbarkeit
- Konsistentes Layout

**Konsequenz**:

- Refactoring der bestehenden Seiten-Header

=== Shared Component: Action Toolbar
**Entscheid**: Bereitstellung der Action Toolbar als wiederverwendbare Shared Component

**Begründung**: 

- Wiederkehrendes UI-Muster auf verschiedenen Ansichten
- Einheitliche Platzierung von Aktions-Schaltflächen

**Konsequenz**:

- Refactoring des bestehenden Codes

=== Generische Tabelle `FitLogTable`
**Entscheid**: Implementierung einer generischen Tabellenkomponente (`FitLogTable`)

**Begründung**: 

- Hohe Wiederverwendbarkeit für unterschiedliche Datensätze
- Vermeidung von doppeltem Tabellencode

**Konsequenz**:

- Die Tabelle unterstützt dynamische Spaltendefinitionen sowie optionale Aktions-Buttons

=== `WorkoutService` für Erstellung und Kalender
**Entscheid**: Der `WorkoutService` wird vom Feature `workout-calendar` und `workouts` verwendet. 

**Begründung**: 

- Vermeidung von Codeduplikaten
- Benötigt die gleichen Daten

**Konsequenz**:

- Höhere Koppelung
- keine Codeduplikate
